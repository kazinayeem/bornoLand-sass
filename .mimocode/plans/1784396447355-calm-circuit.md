# Fix Builder / Live Store Rendering Mismatch

## Root Cause

The codebase has **two completely separate page storage systems** that don't talk to each other:

| System | Model | API Routes | Frontend API | Used By |
|--------|-------|-----------|-------------|---------|
| Legacy Builder | `PageModel` ("Page") | `/builder/*` | `builder-api.ts` | Builder UI Save/Publish |
| New Store Pages | `StorePageModel` ("StorePage") | `/store-pages/*` | `store-page-api.ts` | Dashboard Pages Panel |

**The critical mismatch:**
1. **Builder writes to `PageModel`** (old system) via `builder-api.ts` → `/builder/page/:id/save`
2. **Dashboard Pages Panel writes to `StorePageModel`** (new system) via `store-page-api.ts` → `/store-pages/:id/draft`
3. **Live Store reads from `PageModel`** (old system) via `tenant-resolver.service.ts` → `/public/tenant/:slug`
4. The two models are **different MongoDB collections** — data saved in one is invisible to the other

**Additionally**, `StorefrontPageRenderer` never passes `headerSections` or `footerSections` to `StorefrontShell`, so builder-defined headers/footers never appear on the Live Store even when the data exists.

**Slug format difference:** `PageModel` stores slugs as `"home"` (no leading slash), while `StorePageModel` stores them as `"/"` for home, `"/shop"` for shop, etc. (with leading slash). The migration and tenant resolver must account for this.

**Why the mismatch happened:** The Builder was built first using `PageModel`. Later, a more complete Store Pages system was built using `StorePageModel` (with versioning, soft delete, preview tokens, etc.). The Builder was never migrated to use the new system, and the Live Store's data fetcher was never updated to query the new model.

## Fix: Unify on StorePageModel

### Step 1 — Switch Builder to use `store-page-api.ts`
**File:** `apps/web/src/components/builder/builder-editor.tsx`

Replace imports from `builder-api.ts` with `store-page-api.ts`:
- `useGetPagesQuery` → `useGetStorePagesQuery`
- `useCreatePageMutation` → `useCreateStorePageMutation`
- `useSavePageMutation` → `useSaveStorePageDraftMutation`

Update all call sites to match the new API signatures (e.g. `savePage({ storeId, pageId, data })` → `saveStorePageDraft({ id: pageId, storeId, sections, headerSections, footerSections, ... })`).

**File:** `apps/web/src/components/builder/builder-toolbar.tsx`

Replace:
- `useSavePageMutation` → `useSaveStorePageDraftMutation`
- `usePublishPageMutation` → `usePublishStorePageMutation`

Update `handleSave` and `handlePublish` to use the new endpoints.

### Step 2 — Update Live Store data fetcher
**File:** `apps/api/src/modules/stores/tenant-resolver.service.ts`

Replace `PageModel` import with `StorePageModel`:
```ts
import { StorePageModel } from "../../modules/pages/store-page.model.js";
```

Change the page query to handle the slug format difference (StorePageModel uses leading `/`):
```ts
const normalizedSlug = pageSlug.startsWith("/") ? pageSlug : `/${pageSlug}`;
const page = await StorePageModel.findOne({
  storeId: store._id, slug: normalizedSlug.toLowerCase(), status: "published", deletedAt: null
}).lean();
```

### Step 3 — Pass header/footer sections to the Live Store shell
**File:** `apps/web/src/components/storefront/storefront-page-renderer.tsx`

Extract header/footer sections from page data and pass them:
```tsx
const headerSections = (page?.headerSections as any[]) ?? [];
const footerSections = (page?.footerSections as any[]) ?? [];
const headerSettings = (page?.headerSettings as Record<string, unknown>) ?? {};
const footerSettings = (page?.footerSettings as Record<string, unknown>) ?? {};

return (
  <StorefrontShell
    ...
    pageSections={pageSections}
    headerSections={headerSections}
    footerSections={footerSections}
    headerSettings={headerSettings}
    footerSettings={footerSettings}
    footerSection={footerSection}
  >
    <StorefrontCanvas sections={pageSections} />
  </StorefrontShell>
);
```

### Step 4 — Ensure Builder page creation goes to StorePageModel
**File:** `apps/web/src/components/builder/builder-editor.tsx`

The `createPage` call (line 328) should use `useCreateStorePageMutation` from `store-page-api.ts`. Update the page type derivation and default slug generation to match the new API (slugs need leading `/` for StorePageModel).

### Step 6 — Data migration from PageModel → StorePageModel
**File:** `apps/api/src/modules/pages/migrate-pages.ts` (new)

Create a one-time migration script that:
1. Queries all documents from the `Page` collection (`PageModel`)
2. For each page, checks if a corresponding `StorePage` already exists (match by `storeId` + `slug`)
3. If no matching `StorePage` exists, inserts a new document copying all relevant fields (`sections`, `headerSections`, `footerSections`, `headerSettings`, `footerSettings`, `theme`, `seo`, `status`, `slug`, `title`, etc.)
4. Maps `isHome` → `isHomePage`, converts slug format (`"home"` → `"/"`, `"shop"` → `"/shop"`), adds `pageType`, `sortOrder`, `visibility`, `isSystem` defaults
5. Logs migration results (created count, skipped count)

**File:** `apps/api/src/routes/admin.route.ts` (or a standalone script entry)

Wire the migration as a callable endpoint or CLI script so it can be run once. The migration should be idempotent (safe to run multiple times).
